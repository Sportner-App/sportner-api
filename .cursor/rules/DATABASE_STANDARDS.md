# Database Standards

> This document defines the database design standards for the Sports Companion application.
>
> Every database object must follow these standards.
> Unless explicitly instructed otherwise, these rules are mandatory.

---

# 1. Database

Database Engine

PostgreSQL

Provider

Supabase PostgreSQL

ORM

Entity Framework Core

Migrations

Entity Framework Core Migrations

Database schema

public

---

# 2. Naming Convention

## Tables

Use snake_case.

Use plural names.

Examples

```
users
profiles
events
event_applications
event_messages
reviews
badges
```

---

## Columns

Use snake_case.

Examples

```
created_at
updated_at
first_name
profile_image_url
```

---

## Primary Keys

Always use

```
id
```

Never use

```
user_id
profile_id
```

as the primary key.

---

## Foreign Keys

Always use

```
<entity>_id
```

Examples

```
user_id
event_id
badge_id
sport_id
```

---

## Index Names

Entity Framework default naming is acceptable.

Do not manually rename indexes unless required.

---

# 3. Primary Keys

Every table must use

UUID

Example

```sql
id UUID
```

Primary keys are generated by the application.

Never use integer identity columns.

---

# 4. Foreign Keys

Every relationship must use UUID foreign keys.

Foreign keys must always be explicitly configured using Fluent API.

Never rely on EF conventions alone.

---

# 5. Timestamps

Every table must contain

```
created_at
updated_at
```

Type

TIMESTAMPTZ

Backend

DateTimeOffset

Use UTC only.

Never use local server time.

---

# 6. Audit Fields

Entities that inherit from AuditableEntity must contain

```
created_by_user_id
updated_by_user_id
```

Both fields are nullable.

---

# 7. Soft Delete

Do NOT use

```
deleted_at
is_deleted
```

Deletion must be handled through Status fields when required.

Physical deletion is allowed only for dependent entities where business rules permit.

---

# 8. Status Columns

Status columns use

SMALLINT

Backend uses enums.

Example

```csharp
UserStatus
EventStatus
ApplicationStatus
```

Never store enum names as strings.

---

# 9. Relationships

One-to-One

Use UNIQUE foreign keys.

Example

```
users
profiles
```

One-to-Many

Standard foreign key.

Many-to-Many

Always use an explicit join table.

Example

```
event_participants
user_badges
```

Never use EF Core automatic many-to-many.

---

# 10. Cascade Delete

Default behavior

Restrict

Never enable Cascade Delete by default.

Configure cascade explicitly only when required.

Protect important data from accidental deletion.

---

# 11. Constraints

Always create database constraints.

Examples

Unique username

```
UNIQUE(username)
```

One profile per user

```
UNIQUE(user_id)
```

One sport per user

```
UNIQUE(user_id, sport_id)
```

Do not rely only on application validation.

---

# 12. Indexes

Create indexes only when necessary.

Always index

- Foreign Keys
- Frequently searched fields
- Unique fields

Examples

```
username
phone
event_date
status
```

Avoid unnecessary indexes.

Every index has a write cost.

---

# 13. Text Columns

Use PostgreSQL

TEXT

instead of VARCHAR unless a strict limit is required by business rules.

Examples

```
bio
phone
address
username
```

---

# 14. Numeric Types

Use

SMALLINT

For

- Status
- Enum values
- Rating levels
- Skill levels

Use

INTEGER

For

- Counts
- Totals

Use

NUMERIC

Only when decimal precision matters.

Examples

```
average_rating NUMERIC(2,1)
latitude NUMERIC(9,6)
longitude NUMERIC(9,6)
```

---

# 15. Boolean Columns

Use BOOLEAN.

Avoid nullable booleans unless they represent an unknown state.

---

# 16. File Storage

Images

Videos

Documents

must never be stored inside PostgreSQL.

Use Supabase Storage.

Database stores only file paths.

Example

```
profile_image_url
intro_video_url
```

---

# 17. Entity Configuration

Never use DataAnnotations.

Always configure entities using

```
IEntityTypeConfiguration<T>
```

Every entity must have its own configuration class.

Example

```
UserConfiguration
ProfileConfiguration
EventConfiguration
```

---

# 18. Migrations

Always generate migrations using EF Core.

Never manually modify the production database.

Schema changes must always come from migrations.

One logical change = one migration.

Migration names should be meaningful.

Examples

```
InitialCreate

AddUserSessions

AddEventReviews

CreateFeedTables
```

---

# 19. Seed Data

Only static lookup data may be seeded.

Examples

```
sports

badge_types

notification_types
```

Never seed users.

Never seed events.

Never seed business data.

---

# 20. Performance

Never use SELECT \*.

Always project required fields.

Avoid loading unnecessary navigation properties.

Prefer pagination for collections.

Prefer EXISTS over COUNT when checking existence.

---

# 21. Transactions

Use transactions only when multiple writes must succeed together.

Avoid long-running transactions.

---

# 22. Navigation Properties

Navigation properties should reflect business relationships.

Avoid unnecessary bidirectional navigation.

Do not expose navigation properties that are never used.

---

# 23. Value Objects

Simple values remain primitive types.

Create Value Objects only when business rules justify them.

Examples

Possible future Value Objects

```
PhoneNumber

Coordinates

Location

Money
```

---

# 24. Supabase

Supabase is used only as

- PostgreSQL Database
- Authentication Provider (OTP)
- Storage

Business logic belongs to the backend.

Do not implement business rules using PostgreSQL functions or triggers unless explicitly required.

---

# 25. Cursor Rules

When generating database code:

- Follow these standards strictly.
- Do not invent additional columns.
- Do not introduce new naming conventions.
- Do not create unnecessary indexes.
- Configure every relationship explicitly.
- Generate clean Fluent API configuration.
- Keep entity classes focused on business behavior.
- If requirements are missing, stop and explain instead of guessing.
