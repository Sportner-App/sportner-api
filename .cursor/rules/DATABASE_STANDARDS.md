# Database Standards

> This document defines the database design standards for the Sports Companion application.
>
> Every database object must follow these standards.
> Unless explicitly instructed otherwise, these rules are mandatory.

---

# 1. Database

Database Engine

PostgreSQL

Provider

Supabase PostgreSQL

ORM

Entity Framework Core

Migrations

Entity Framework Core Migrations

Database schema

public

---

# 2. Naming Convention

## Tables

Use EF Core conventions through plural `DbSet` property names.

Physical table names use PascalCase plural names.

Examples

```
Users
Profiles
Events
EventParticipants
Messages
Reviews
Badges
```

---

## Columns

Use the entity property name generated by EF Core conventions.

Examples

```
CreatedAt
UpdatedAt
FirstName
ProfileImageUrl
```

---

## Primary Keys

Always use

```
Id
```

Never use

```
UserId
ProfileId
```

as the primary key.

---

## Foreign Keys

Always use

```
<Entity>Id
```

Examples

```
UserId
EventId
BadgeId
SportId
```

---

## Index Names

Entity Framework default naming is acceptable.

Do not manually rename indexes unless required.

---

# 3. Primary Keys

Every table must use

UUID

Example

```sql
id UUID
```

Primary keys are generated by the application.

Never use integer identity columns.

---

# 4. Foreign Keys

Every relationship must use UUID foreign keys.

Prefer EF Core relationship conventions when navigation and foreign-key properties
follow the `<Entity>` / `<Entity>Id` naming pattern.

Do not add per-entity Fluent API configuration merely to repeat a convention.
Use minimal explicit model configuration only when a documented relationship,
delete behavior, index, precision, conversion, or constraint cannot be represented
correctly by conventions.

---

# 5. Timestamps

Every table must contain

```
CreatedAt
UpdatedAt
```

Type

TIMESTAMPTZ

Backend

DateTimeOffset

Use UTC only.

Never use local server time.

---

# 6. Audit Fields

Entities that inherit from AuditableEntity must contain

```
CreatedByUserId
UpdatedByUserId
```

Both fields are nullable.

---

# 7. Soft Delete

Do NOT use

```
deleted_at
is_deleted
```

Deletion must be handled through Status fields when required.

Physical deletion is allowed only for dependent entities where business rules permit.

---

# 8. Status Columns

Status columns use

SMALLINT

Backend uses enums.

Example

```csharp
UserStatus
EventStatus
ApplicationStatus
```

Never store enum names as strings.

---

# 9. Relationships

One-to-One

Use UNIQUE foreign keys.

Example

```
users
profiles
```

One-to-Many

Standard foreign key.

Many-to-Many

Always use an explicit join table.

Example

```
event_participants
user_badges
```

Never use EF Core automatic many-to-many.

---

# 10. Cascade Delete

Default behavior

Restrict

Never enable Cascade Delete by default.

Configure cascade explicitly only when required.

Protect important data from accidental deletion.

---

# 11. Constraints

Always create database constraints.

Examples

Unique username

```
UNIQUE(username)
```

One profile per user

```
UNIQUE(user_id)
```

One sport per user

```
UNIQUE(user_id, sport_id)
```

Do not rely only on application validation.

---

# 12. Indexes

Create indexes only when necessary.

Always index

- Foreign Keys
- Frequently searched fields
- Unique fields

Examples

```
username
phone
event_date
status
```

Avoid unnecessary indexes.

Every index has a write cost.

---

# 13. Text Columns

Use PostgreSQL

TEXT

instead of VARCHAR unless a strict limit is required by business rules.

Examples

```
bio
phone
address
username
```

---

# 14. Numeric Types

Use

SMALLINT

For

- Status
- Enum values
- Rating levels
- Skill levels

Use

INTEGER

For

- Counts
- Totals

Use

NUMERIC

Only when decimal precision matters.

Examples

```
average_rating NUMERIC(2,1)
latitude NUMERIC(9,6)
longitude NUMERIC(9,6)
```

---

# 15. Boolean Columns

Use BOOLEAN.

Avoid nullable booleans unless they represent an unknown state.

---

# 16. File Storage

Images

Videos

Documents

must never be stored inside PostgreSQL.

Use Supabase Storage.

Database stores only file paths.

Example

```
profile_image_url
intro_video_url
```

---

# 17. Entity Configuration

The default persistence style is convention-first, matching the TMS API:

- Add plural `DbSet<TEntity>` properties to `AppDbContext`.
- Let EF Core infer tables, columns, keys and standard relationships.
- Keep Domain entities free of persistence-only attributes where possible.
- Do not create one `IEntityTypeConfiguration<T>` per entity by default.

Fluent API remains allowed for exceptions that conventions cannot express safely,
such as composite unique indexes, non-default delete behavior, precision, enum
conversion, or relationships without navigation properties. Keep any such mapping
minimal and centralized in Infrastructure.

---

# 18. Migrations

Always generate migrations using EF Core.

Never manually modify the production database.

Schema changes must always come from migrations.

One logical change = one migration.

Migration names should be meaningful.

Examples

```
InitialCreate

AddUserSessions

AddEventReviews

CreateFeedTables
```

---

# 19. Seed Data

Only static lookup data may be seeded.

Examples

```
sports

badge_types

notification_types
```

Never seed users.

Never seed events.

Never seed business data.

---

# 20. Performance

Never use SELECT \*.

Always project required fields.

Avoid loading unnecessary navigation properties.

Prefer pagination for collections.

Prefer EXISTS over COUNT when checking existence.

---

# 21. Transactions

Use transactions only when multiple writes must succeed together.

Avoid long-running transactions.

---

# 22. Navigation Properties

Navigation properties should reflect aggregate ownership.

Avoid unnecessary bidirectional navigation.

Do not expose navigation properties that are never used.

Keep cross-aggregate references as identifiers in the Domain model. Configure their
database foreign keys explicitly in Infrastructure and read across aggregates through
CQRS projections/joins. Do not add navigation properties merely to enable deep `Include`
graphs.

---

# 23. Value Objects

Simple values remain primitive types.

Create Value Objects only when business rules justify them.

Examples

Possible future Value Objects

```
PhoneNumber

Coordinates

Location

Money
```

---

# 24. Supabase

Supabase is used only as

- PostgreSQL Database
- Authentication Provider (OTP)
- Storage

Business logic belongs to the backend.

Do not implement business rules using PostgreSQL functions or triggers unless explicitly required.

---

# 25. Cursor Rules

When generating database code:

- Follow these standards strictly.
- Do not invent additional columns.
- Do not introduce new naming conventions.
- Do not create unnecessary indexes.
- Prefer EF Core conventions and plural DbSet names.
- Add explicit mapping only when convention output would violate a documented invariant.
- Keep entity classes focused on business behavior.
- If requirements are missing, stop and explain instead of guessing.
