# Notifications

## Module

Social

## Aggregate Root

Notification

---

# Purpose

The `notifications` table stores all in-app notifications generated by user interactions across the platform.

Notifications provide users with real-time updates about activities related to their account, including social interactions, event participation, friendships, chat messages, badges and system announcements.

This table serves as the central notification hub for the application.

---

# Responsibilities

- Store in-app notifications
- Track notification read status
- Support all application modules
- Provide notification history
- Enable push notification synchronization

# Business Rules

- Every notification belongs to exactly one recipient.
- Notifications may optionally reference the user who triggered the action.
- Notifications may reference any application entity through `entity_type` and `entity_id`.
- Users cannot generate notifications for their own actions.
- Notifications are immutable after creation except for read status.
- Marking a notification as read sets both `is_read` and `read_at`.
- Notifications are retained as user history unless explicitly removed by the user.
- Push notifications are generated from the same events but are managed independently.

# Lifecycle

## Create Notification

- Validate recipient.
- Create notification.
- Deliver push notification if enabled.
- Persist notification history.

---

## Read Notification

- Validate ownership.
- Set `is_read = true`.
- Set `read_at`.

---

## Delete Notification

- Validate ownership.
- Permanently remove the notification.

# Performance Notes

Most queries retrieve notifications by:

- recipient_user_id
- is_read
- created_at

Notification lists should always be ordered by:

- created_at DESC

Unread counts should use indexed queries.

Cursor pagination should be used for large notification histories.

# Notes

Notifications are generated automatically by backend business logic.

The notification text should be localized before being presented to the user.

This table stores only notification metadata and history.

Push notifications, email notifications and in-app notifications all originate from the same notification event.

The combination of `notification_type`, `entity_type` and `entity_id` allows a single notification infrastructure to support every module in the application without introducing additional notification tables.
