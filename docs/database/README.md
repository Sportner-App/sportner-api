# Sports Companion - Database Architecture

## Overview

This document defines the database architecture of the Sports Companion platform.

The database is designed around modular domains, following Clean Architecture and Domain-Driven Design (DDD) principles.

The primary goal is to create a scalable, maintainable and production-ready data model that supports long-term product evolution.

The database serves as the single source of truth for all business data.

---

# EF Core Naming Policy

Physical PostgreSQL identifiers follow EF Core conventions, matching the TMS API:

- plural `DbSet` property names become table names (`PostComments`)
- entity property names become column names (`PostId`, `CreatedAt`)
- primary keys use `Id`
- foreign-key properties use `<Entity>Id`

Some per-table documents still use snake_case identifiers as logical/legacy names.
Their data types, nullability, relationships, constraints, indexes and business rules
remain authoritative; identifier casing is normalized by this convention-first policy.

# Design Principles

The following principles apply to every table in the database.

## Single Responsibility

Each table must have a single business responsibility.

A table should never contain unrelated business data.

Examples

- users → Authentication and account lifecycle
- user_profiles → Public profile information
- user_statistics → User statistics
- user_sports → Sports and skill levels
- events → Event information

---

## Normalization

The database follows relational design principles.

Business data should be normalized unless a denormalized structure provides measurable performance benefits.

JSON/JSONB columns must not be used for business entities.

---

## UUID Primary Keys

Every table uses UUID as its primary key.

Example

```sql
id UUID PRIMARY KEY
```

UUIDs are generated by the backend application.

---

## Audit Fields

Every business table inherits the following audit fields.

```text
created_at
updated_at
created_by_user_id
updated_by_user_id
```

Audit fields are inherited from the application's AuditableEntity.

---

## Soft Delete

The application does not use deleted_at or is_deleted columns.

Instead, lifecycle is managed through status fields.

Example

```text
Active
Suspended
Blocked
Deleted
```

---

## File Storage

Images, videos and documents are stored in Supabase Storage.

Only file paths are stored in PostgreSQL.

Example

```text
profile_image_url
intro_video_url
media_url
```

---

## Enum Strategy

Every enum is stored as SMALLINT.

Examples

- UserStatus
- EventStatus
- SkillLevel
- ConversationType
- MessageType

Enum names are never stored in the database.

---

## Foreign Keys

All foreign keys use UUID.

Naming convention

```text
user_id
event_id
sport_id
conversation_id
```

---

## Constraints

Database constraints are mandatory.

Examples

- UNIQUE(phone_number)
- UNIQUE(user_id)
- UNIQUE(user_id, sport_id)

Business rules should be protected at database level whenever possible.

---

## Index Strategy

Indexes are created only when necessary.

Default indexed fields

- Foreign Keys
- Frequently queried columns
- Unique columns
- Status columns
- Date columns used for sorting

Avoid unnecessary indexes.

# Domain Modules

The database is organized into independent business modules.

---

## Identity

Responsible for authentication, profile management and user account lifecycle.

Tables

```text
users
user_profiles
user_sessions
user_devices
user_statistics
user_saved_locations
user_sports
```

---

## Sports

Responsible for predefined sports supported by the platform.

Tables

```text
sports
```

---

## Events

Responsible for event creation and participation.

Tables

```text
events
event_participants
event_waitlist
```

---

## Messaging

Responsible for conversations and messaging.

The messaging infrastructure is designed to support both event chats and future direct messaging.

Tables

```text
conversations
conversation_members
messages
```

Conversation types

- Event
- Direct (Future)
- Group (Future)

Tables

```text
reviews
```

Tables

```text

posts
```

## Notifications

Tables

# Database Philosophy

The database is designed to be:

- Modular
- Relational
- Explicit
- Predictable
- Easy to evolve
- Easy to maintain

Every table should represent a business concept.

Every relationship should be explicit.

Every business rule should be enforceable.

The database should remain understandable even as the application grows over time.
